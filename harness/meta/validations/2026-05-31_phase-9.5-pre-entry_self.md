## 검증 결과 (V1~V7)

### V1. eval mock-deterministic primary (CI 가능, 비용 0) — PASS

- **self-question**: golden_set 회귀 runner 를 **mock-deterministic primary** (실 LLM 호출 없이 결정적 mock pipeline) 로 구축하고 실 LLM 은 mode flag + 문서로 두는 것(사용자 결정)이 CI 가능성·비용·회귀 baseline 신뢰성 측면에서 정합하며, golden_set §4.2 fast/full/batch + §8.2 "mock 우선" open question 과 정합하는가?
- **self-answer**:
  - **현 상태 (golden_set/regression_eval 정독)**: golden_set §4.2 실행 모드(fast/full/batch)는 실 LLM 호출 가정 (§4.3 모델 + temperature override). regression_eval §8.1 "CI 비용 full mode ~$0.5/회, 월 ~$15" + §8.2 "mock RAG vs 실 RAG 트레이드오프" + golden_set §8.2 "GS-007 mock vs 실 검색, 현재 mock 우선" — 즉 mock 우선 정책은 이미 문서에 내장.
  - **mock-deterministic 정의**: runner 는 실 LLM(`run_critic`/Planning) 을 호출하지 않고, 각 GS 케이스의 `expected_*` 와 결정적 mock pipeline 출력(고정 시드 / fixture)을 비교한다. 채점은 schema 준수 + structural(규칙 기반) 차원 (V6). 비결정성(temperature/모델 변동) 0 → 동일 입력 동일 결과 → CI per-commit 가능 + 비용 0.
  - **정합 근거**: ① Phase 9 baseline test 는 이미 OpenAI client mock 주입 패턴(test_critic / test_moa_orchestrator) — runner 도 동일 패턴 재사용. ② mock-deterministic 은 schema 회귀 + structural 회귀(plan 3개 / hook 존재 / flow 비트 / 광고 단어 부재 / 차단 단어)를 100% 커버 → prompt/RAG/모델 변경 시 "구조 회귀" 자동 감지(확정 결정 [20] semver 회귀 baseline). ③ 실 LLM 8차원 품질 채점(intent_fit 등 의미 점수)은 비결정적 → mode flag(`--mode=real`) + 문서(운영 단계 야간 배치)로 분리 (NG2).
  - **한계 (정직)**: mock-deterministic 은 "의미 품질"(hook 매력도 / 의도 적합도)을 대리하지 못함 — 구조/형식 회귀만. 이 한계는 U2 로 명시 + 실 LLM mode 로 보완 (운영 단계).
- **잠재 risk**:
  - mock-deterministic 이 실 LLM 품질 신호를 충분히 대리하는지 (U2) → schema/structural 범위 명시 + 실 LLM mode flag 문서로 한계 인정.
  - mock fixture 가 golden_set expected 와 drift → loader 가 golden_set.md 를 단일 출처로 파싱(중복 정의 금지, V2).
- **권장**:
  - ADR-033 §Decision 에 "runner mock-deterministic primary (실 LLM 미호출, 결정적 fixture/seed) + 실 LLM mode flag(`--mode=real`) 문서 — CI per-commit 가능 + 비용 0, schema/structural 차원" 명시.
  - ADR-033 §Constraints 에 "mock-deterministic 은 구조/형식 회귀 대리 (의미 품질 X — U2), 실 LLM 8차원 채점은 mode flag + 운영 야간 배치(NG2)" 명시.
  - Slice 2 `test_eval_runner.py` 에 mock pipeline 결정성(동일 입력 2회 동일 출력) 케이스.

### V2. golden_set 케이스 markdown → 구조화 파싱 (loader 설계 근거) — PASS

- **self-question**: `eval/golden_set.md` 의 GS-XXX 케이스(YAML 블록 in markdown)를 loader 가 `{id, input, expected_properties}` 구조로 파싱 가능한가? golden_set.md 를 단일 출처로 유지(중복 정의 금지)하며 executable format 을 도출할 수 있는가?
- **self-answer**:
  - **현 상태 (golden_set §1/§2 정독)**: 각 케이스는 ` ```yaml ... ``` ` fenced code block 안에 `case_id` / `name` / `priority` / `mode` / `prompt_target` / `input` / `expected_path` / `expected_output(body_keys + validation + passing_criteria)` / `notes` 키를 가진 표준 YAML. §1 에 표준 형식이 단일 정의되어 있고 §2 에 GS-001~GS-011 인스턴스가 있음. 즉 markdown 안의 YAML 블록은 기계 파싱 가능한 구조.
  - **파싱 전략 (loader 설계)**: golden_set_loader 는 golden_set.md 를 읽어 ` ```yaml ` 블록을 추출 → 각 블록을 `yaml.safe_load` → `case_id` 가 있는 dict 만 케이스로 수집 → `{id: case_id, mode, prompt_target, input, expected: {body_keys, validation, passing_criteria}}` 구조화. golden_set.md 가 **단일 출처** (loader 는 별도 케이스 정의 X — 파싱만). NG10 정합 (11 케이스 그대로, 확대 X).
  - **executable format 도출**: structured 케이스는 runner 가 소비할 수 있는 형태 — `body_keys` 는 schema 준수 검증, `validation` 규칙(예: "cards.length == 4", "plans[*].rag_used.length ≤ 3")은 structural 채점 룰로 매핑(자동 가능한 규칙만 — 자유 텍스트 "LLM-as-judge" 항목은 실 LLM mode), `passing_criteria` 는 케이스 단위 합/불.
  - **회귀 0**: loader 는 golden_set.md 를 읽기만(수정 X — eval/golden_set.md forbidden in Slice 1~4 except contract-change). 신규 module 추가만 → 기존 코드 0 변경.
  - **자동 vs 비자동 규칙 구분**: validation 규칙 중 정확 매칭/길이/배열 길이/광고 단어 부재 = mock 자동 가능. "카드별 의미 중첩 < 30% (LLM-as-judge)" / "missing_info 의미 판단" = 실 LLM mode (V6 채점 차원 분리).
- **잠재 risk**:
  - markdown YAML 블록 중 케이스가 아닌 블록(§1 표준 형식 template / §5.2 jsonl 스키마 예시 등)을 케이스로 오인 → `case_id` 키 존재 + `GS-` prefix 필터로 배제(U1 — Slice 2 loader 확정).
  - validation 규칙의 자유 텍스트 표현(자연어)을 자동 룰로 전부 매핑 불가 → 자동 가능 규칙만 mock, 나머지는 실 LLM mode 표시(부분 채점).
- **권장**:
  - ADR-033 §eval-design 에 "golden_set_loader: golden_set.md ` ```yaml ` 블록 → `case_id` GS- prefix 필터 → `{id, mode, prompt_target, input, expected_properties}` 구조화. golden_set.md 단일 출처(loader 파싱만, 케이스 정의 X)" 명시.
  - Slice 2 loader 에 §1 template 블록 / §5.2 예시 블록 배제(GS- prefix gate) + 11 케이스 전부 로드 케이스.
  - validation 규칙 자동/비자동 분류표 ADR-033 §eval-design 에 첨부.

### V3. revise effect metric (mock — revise attempt별 canonical score 변화) — PASS

- **self-question**: Phase 4.5 D6 부터 미측정이던 revise loop 개선 효과를 mock-based metric(revise attempt별 canonical score 변화)으로 측정하는 것이 정합하며, 실 revise 동작을 충분히 대리하는가?
- **self-answer**:
  - **현 상태 (D6 누적 6회 deferred)**: Phase 4.5 에서 revise loop(Critic → Rewriter → 재평가, max 2) 구현. 그러나 "revise 가 실제 품질을 올리는가" 의 effect metric 은 Phase 4.5/6/7/8/9 내내 deferred(D6, 누적 6회). GS-005(revise 1회 → approve) / GS-006(revise 2회 → forced_approve) 케이스가 revise 흐름 회귀를 정의하나 effect(점수 delta) 측정은 없음.
  - **mock metric 정의**: revise_effect 는 revise attempt 별 canonical score(overall_score 0–1) 변화를 측정 — `attempt 0 (초기 critic)` → `attempt 1 (revise 후 재평가)` → `attempt 2`. mock 환경에서는 결정적 revise fixture(각 attempt 의 verdict)를 입력으로 `delta = score[n] - score[n-1]` 산출 + 방향성(증가/정체/감소) 집계. revise_history(Body.revise_history — Phase 4.5 ADR-016 구조, plan별 attempt list)와 정합.
  - **정합 근거**: ① revise_history 는 이미 attempt 별 dict(ReviseAttempt 모델 — attempt/action/revised)를 누적 → mock fixture 가 canonical score 를 attempt 별로 제공하면 delta 산출 결정적. ② canonical(overall_score 0–1)은 Phase 9 wiring 으로 live(normalize_to_canonical) → revise effect 도 canonical 기준(0–5 deprecated 불필요 — V4 제거 정합). ③ mock 이므로 비용 0 + CI 가능(V1 정합).
  - **한계 (정직)**: mock fixture 의 score delta 는 "설계상 revise 가 올린다고 가정한" 값 — 실 LLM 이 실제로 올리는지는 실 LLM mode(U5). mock 은 "revise loop 가 attempt 별 score 를 집계/리포트하는 메커니즘" 회귀 검증 + 구조 검증. 실 effect 크기는 운영 단계.
- **잠재 risk**:
  - mock metric 이 실 개선을 대리하지 못함(U5) → mock 은 메커니즘/구조 회귀, 실 effect 는 실 LLM mode 명시.
  - revise_history 구조 변경 시 revise_effect drift → revise_history(ReviseAttempt) 단일 출처 정합.
- **권장**:
  - ADR-033 §eval-design 에 "revise_effect metric: revise attempt 별 canonical overall_score(0–1) delta + 방향성 집계 (mock fixture 결정적). revise_history(ReviseAttempt) 정합. 실 effect 크기는 실 LLM mode(U5)" 명시.
  - Slice 3 `test_revise_effect.py` 에 attempt 0→1→2 score delta + 방향성 + revise 없는 케이스(delta=0) 케이스.

### V4. Critic deprecated 제거 경계 (run_critic 0–5 불변 P-007, fallback + schema Optional만) — PASS

- **self-question**: Critic deprecated 0–5 Full 제거 대상이 정확히 `select_best_plan_index` deprecated fallback branch(overall_score_avg / scores / eight_dim_scores + DeprecationWarning) + `CriticEvaluation` Optional deprecated 필드로 한정되고, `run_critic` 0–5 출력(P-007 prompt contract) + `normalize_to_canonical` 0–5→0–1 변환은 불변(NG3)인 경계가 명확한가?
- **self-answer**:
  - **현 상태 (critic.py 정독)**: ① `run_critic` 은 LLM 에 0–5 8차원 산출 요청(SYSTEM_PROMPT) → `norm_scores`(0~5 clamp) + `overall_score_avg`(0–5 평균) + verdict 반환 — **P-007 prompt contract (LLM-facing 0–5)**. ② `normalize_to_canonical(verdict)` 은 비파괴 사본 + `dimensions[k] = scores[k]/5.0` + `overall_score = overall_score_avg/5.0` 추가(0–5 읽어 0–1 생성). ③ `select_best_plan_index` 은 canonical(overall_score → dimensions) 우선 + **deprecated fallback**(overall_score_avg → scores/eight_dim_scores + `warnings.warn(DeprecationWarning)`, line 372~401) — Phase 9 wiring 으로 canonical 항상 populated → 이 fallback 은 **dead code**.
  - **제거 대상 (정확 경계)**: ⓐ `select_best_plan_index` 의 deprecated fallback branch (overall_score_avg / scores / eight_dim_scores 소비 3 branch + DeprecationWarning 3 발행) — canonical 우선 로직(overall_score / dimensions)만 남김. ⓑ `CriticEvaluation`(schemas/output.py) Optional deprecated 필드 — `scores(CriticScores | None)` / `overall_score_avg(float | None)` / `target_plan_id` / `reasons` / `suggestions` 중 deprecated 표시된 0–5 필드(scores / overall_score_avg) 제거 → canonical(overall_score + dimensions) + overall_verdict + blocking_issues + revise_round 만.
  - **불변 (제거 X — NG3)**: ① `run_critic` 의 0–5 출력(norm_scores dict + overall_score_avg) — P-007 prompt contract. LLM 이 0–5 산출 → normalize 가 0–1 변환. critic.py forbidden(run_critic 로직). ② `normalize_to_canonical` 의 0–5→0–1 변환 로직(scores 읽어 dimensions 생성) — 유지(canonical 생성의 단일 경로). ③ SYSTEM_PROMPT 0–5 차원 정의 — P-007 prompt 불변.

Pydantic `extra='ignore'`(또는 normalize 후 canonical만 추출) 로 verdict 의 0–5 키를 schema 가 무시 → 회귀 0.
  - **회귀 0 근거**: select_best_plan_index fallback 은 dead(canonical 항상 존재) → 제거 시 동작 동일 + DeprecationWarning 감소(Phase 9 67→16 의 16 잔존분 추가 해소). CriticEvaluation 0–5 필드는 이미 Optional(default None) → 제거 시 canonical 경로 불변 (단, frontend non-optional 정합 V7 + 의도 delta test V5 처리 필요).
- **잠재 risk**:
  - "deprecated 제거 김에 run_critic 0–5 도 제거" → NG3 위반 (P-007 prompt contract). ADR-034 §Constraints 명시.

  - select_best_plan_index fallback 제거로 깨지는 test_critic 케이스 수(U4) — Slice 4 pytest 확정.

### V5. 제거 순서 (eval runner → 검증 → 제거) — PASS

- **self-question**: Slice 2~3 에서 eval runner 를 먼저 구축하고 canonical-only 품질 baseline 을 검증한 뒤 Slice 4 에서 deprecated 를 제거하는 순서가 안전성·회귀 추적 측면에서 정합하며, test_critic 의 deprecated-fallback `pytest.warns` 케이스가 유일한 의도 delta 인가?
