# Q&A 대비 답안 — Dreammate Studio 중간 발표

> `resources/03-qna-prep.md`의 31개 질문에 대한 프로젝트 기반 답안.
> 형식 권장: "1초 침묵 → 좋은 질문입니다 → 핵심 2가지 → 우리의 선택과 이유."
> 모르는 것은 솔직히: "정확히 모릅니다. 확인해서 알려드리겠습니다." (거짓보다 +점수)

---

## A. 기획 / 비전

**1. 한 줄로 이 프로젝트는?**
영상을 만들기 전 단계의 기획을 도와주는 AI 에이전트입니다. 막연한 아이디어를 브랜드 방향·타깃·메시지·기획안·실행계획(WBS)까지 연결합니다. 영상 제작이 아니라 영상"기획"입니다.

**2. 누구를 위한 앱인가요?**
1차 타깃은 1인 마케터·소규모 브랜드 운영자·콘텐츠 크리에이터입니다. 외주는 부담스럽고(편당 50만원~), 혼자 기획하기엔 품질에 자신이 없는 사람들입니다.

**3. 비슷한 서비스 대비 차별점은?**
ChatGPT 같은 범용 LLM은 영상 도메인 지식이 얕고 매번 처음부터입니다. 저희는 ① 영상기획 특화 ② **4계층 지식 구조(Brand→Domain→Series→Video)에 누적** ③ 쓸수록 내 브랜드에 맞춰지는 개인화. 실험에서 일반 품질 차이는 작았지만(Δ+0.008), **브랜드 적합도 차이는 컸습니다(Δ+0.425).** 그래서 "더 잘 만든다"가 아니라 "내 브랜드에 맞게, 누적해서"가 진짜 moat입니다.

**4. 핵심 기능 하나만 꼽으면?**
MOA Lite 파이프라인 — Intent→RAG→Planning→**Critic 재작성(최대 2회)**. 생성으로 끝나지 않고 품질을 평가해 다시 쓰게 하는 부분입니다.

**5. Won't(이번에 안 한 것)는? 왜?**
영상 제작 일체(자동 편집·TTS·BGM·자동 업로드)는 **영구 제외**입니다. 이미 도구가 많고, GPU/스토리지 비용이 크며, 우리 차별 가치는 "기획 품질"이기 때문입니다. `mvp_non_goals.md`에 계약으로 박아 뒀습니다.

## B. 기술 선택

**6. 왜 Next.js(PWA)인가요?**
주 타깃이 모바일 마케터라 설치 없는 PWA로 모바일 친화 + 빠른 반복 개발이 필요했습니다. React 생태계와 SSR/라우팅이 기본 제공됩니다. 네이티브 앱(Expo)은 Phase 21+로 미뤘습니다.

**7. 백엔드는 왜 FastAPI(Python)?**
AI/LLM/RAG 생태계가 Python 중심입니다. 에이전트·임베딩·평가 코드와 API를 한 언어로 묶어 인지 부하를 줄였습니다. Pydantic v2로 입출력 스키마를 강제합니다.

**8. DB는 왜 Supabase?**
1인 개발이라 Auth + PostgreSQL + 벡터검색(pgvector)을 한 곳에서 해결하는 게 컸습니다. RLS로 사용자 격리도 됩니다. 직접 구축은 운영 부담이 큽니다.

**9. 대안과 비교했나요?**
LLM은 단일 모델 종속을 피하려고 OpenAI·Claude·Gemini를 추상화한 **Gateway**를 뒀고, 3사 동시 생성도 라이브로 검증했습니다. 벡터 DB는 Pinecone/Weaviate 대신 pgvector로 충분하다고 판단(Phase 21+ 재검토).

**10. 다시 시작한다면?**
테스트 자동 실행 CI를 처음부터 깔았을 겁니다. 지금은 로컬에서 수동으로 게이트를 통과시키는데, "자동 통과 ≠ 실제 동작"을 라이브에서 한 번 데였습니다.

## C. 아키텍처

**11. 화면 1개의 데이터는 어디서 어떻게 오나요?**
프론트(Next.js) → FastAPI(BFF) → AI 엔진(MOA) → Supabase. 예: 기획안 화면은 `/plans/{id}` API로 백엔드에 요청하고, 백엔드가 저장된 후보/Critic 평가를 내려줍니다.

**12. API 호출은 어느 레이어에서?**
프론트는 직접 LLM을 부르지 않습니다. 모든 외부 호출(LLM/DB)은 FastAPI 레이어에서만 일어납니다. 키 노출 방지 + 비용/로그 통제를 한 곳(Gateway)에 모으기 위해서입니다.

**13. 오프라인에서는?**
PWA지만 오프라인 생성은 미지원입니다(LLM 호출 필요). 키/DB가 없으면 graceful degradation — 백엔드는 뜨고 mock으로 응답하되 저장은 휘발됩니다.

**14. 같은 데이터를 여러 화면에서 쓸 때 동기화는?**
서버(Supabase)가 단일 진실 소스이고, 화면은 plan_id 기준으로 다시 읽습니다. 클라이언트 장기 캐시는 두지 않았습니다(MVP 단순화).

**15. 화면 추가 시 만드는 파일은?**
`apps/web/app/<route>/page.tsx` + 필요한 `components/`. 백엔드 계약이 바뀌면 `docs/contracts/`를 절차(contract-change)로 수정합니다.

## D. 개발자 기본 소양 (★ 배점 25점 — 또박또박)

**16. 환경 설정을 처음부터?**
백엔드: `cd harness/backend/fastapi → venv → pip install -r requirements.txt → .env에 OPENAI_API_KEY → harness/에서 uvicorn 기동`. 프론트: `cd harness/apps/web → npm install → npm run dev`. 전체는 `docs/setup.md`에 정리돼 있습니다. **키가 없어도 graceful하게 기동**되도록 설계했습니다.

**17. 빌드는 어떤 명령으로?**
프론트는 `npm run build`(Next.js 14, 14개 라우트). 백엔드는 인터프리터라 별도 빌드가 없고 `typecheck`는 프론트 `tsc --noEmit`로 합니다.

**18. 배포는 어떤 단계로?**
현재 자동 배포되는 건 발표 사이트입니다 — `main`에 `docs/**`가 push되면 GitHub Actions(`pages.yml`)가 GitHub Pages로 올립니다. 앱(프론트/백엔드) 운영 배포는 아직 미연결이고 배포 Gate(Phase 28+)로 잡아 뒀습니다. **솔직히, 운영 배포는 다음 단계입니다.**

**19. 테스트는 어떻게 작성·실행?**
pytest 기반, `harness/`에서 `python -m pytest`로 **814개 케이스**가 키 없이(mock-deterministic) 돌아갑니다. 시나리오 시뮬레이션 36/36도 회귀 게이트입니다. 테스트는 기능 슬라이스마다 추가하며, "기존 테스트 0 수정 + 새 테스트 추가"를 원칙으로 했습니다.

**20. CI/CD가 있나요? 없다면 왜?**
**정직하게 — 발표 사이트 배포 CI(pages.yml)는 있지만, 테스트/빌드 자동 CI는 아직 없습니다.** 1인+AI로 빠르게 가느라 로컬 게이트로 대신했는데, 이게 가장 우선순위 높은 보강 항목입니다. GitHub Actions에 pytest를 올리는 게 다음 작업입니다.

## E. AI Agent 활용 (★ 솔직성 — 숨기면 감점)

**21. AI Agent를 어떻게 활용했나요?**
이 프로젝트는 **하네스(harness) 기반으로 Claude·GPT 같은 AI 에이전트와 함께 설계·구현·검증**했습니다. 단순히 "코드 짜줘"가 아니라, Phase 단위로 범위를 정하고, 계약(contract) 문서로 결정을 고정하고, 중요한 결정은 여러 LLM에 교차검증(multi-llm-validation)하는 방식으로 운영했습니다.

**22. 어디까지 AI가, 어디까지 본인이?**
코드 대부분의 초안은 AI가 생성했습니다. 제가 한 것은 — **무엇을 만들지(범위·우선순위) 결정, 아키텍처·기술스택 판단, AI 산출물 검토·수정, 그리고 "진짜 동작하는지" 라이브 검증**입니다. 예를 들어 "1차 MVP를 더 만들지 vs 이미 만든 걸 실사용 가능하게 마감할지"는 제가 레포 근거로 판단해 후자로 정했습니다.

**23. AI 코드를 본인이 수정한 사례?**
네. 로그인/회원가입에서 쿠키 `secure` 플래그 때문에 로컬에서 인증이 안 되던 버그, 그리고 이메일 형식 오류(422) 메시지가 뭉뚱그려지던 것을 직접 잡아 수정했습니다. AI가 만든 영속 코드도 실제 DB 스키마와 안 맞아 제가 컬럼 구조를 분해해 고쳤습니다(아래 25번).

**24. 본인만의 AI 활용 기법은? (가산점)**
세 가지입니다 — ① **계약-우선**: contracts 폴더를 단일 진실 소스로 두고 AI가 함부로 못 바꾸게 절차화. ② **교차검증**: 큰 결정은 Claude/GPT/Gemini에 각각 물어 합의/불일치를 기록. ③ **gated/behavior-preserving**: 새 기능은 기본 OFF로 넣어 기존 동작을 한 줄도 안 바꾸고(byte-identical) 검증 후 켜기.

**25. AI에게 헛발질당한 사례?**
네, 결정적인 게 있습니다. 자동 테스트는 전부 통과(green)했는데, **실제 Supabase에 저장하려니 AI가 만든 코드가 존재하지 않는 컬럼에 넣으려 해서 실패**했습니다. mock 테스트가 실제 DB 스키마를 강제하지 않아 못 잡은 거죠. 라이브 데모에서 처음 발견했고, 그래서 "**자동 통과 ≠ 실제 동작**"을 교훈으로 못박았습니다.

## F. 협업 (해당 시)

**26. 작업 분담은?**
(2인 팀이면) 역할 분담 설명. 1인이면: "AI 에이전트를 협업 파트너로 두고, 제가 PM/리뷰어 역할, AI가 구현 드래프트 역할로 분담했습니다."

**27. 의사결정이 안 맞았을 때?**
여러 모델 의견이 갈리면 레포 근거(roadmap/scope/contract)로 판정했습니다. 예: GPT가 "2차 기능 만들자" 했지만 레포를 보니 코드는 됐고 운영층이 갭이라, "실사용 마감"으로 정정했습니다.

**28. 짝의(또는 AI의) 코드를 설명할 수 있나요?**
네. 파이프라인 흐름, 영속 구조, gated flag 설계까지 설명 가능합니다. 설명 못 하는 부분은 솔직히 "그 부분은 확인하겠다"고 합니다.

## G. 회고

**29. 가장 어려웠던 부분은?**
"만들었는데 안 보인다" — 기능을 안전하게 기본 OFF로 넣다 보니 사용자가 못 쓰는 상태가 됐던 점, 그리고 자동 테스트가 통과해도 실제 환경에선 깨질 수 있다는 점입니다.

**30. 1주일 더 있다면?**
① pytest CI 구축 ② 프론트를 "진짜 에이전트 같은" UX로 고도화 ③ 5~10명 실사용 + 사람 품질 채점.

**31. 무엇을 배웠나요?**
AI로 빠르게 많이 만들 수 있지만, **"동작 검증"과 "범위 판단"은 사람이 책임져야** 한다는 것. 그리고 정직한 자체 진단(코드 高/운영 中/품질 弱)이 다음 우선순위를 정확히 잡아준다는 것입니다.
